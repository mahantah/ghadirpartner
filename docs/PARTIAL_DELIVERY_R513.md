# Management partial delivery without completing payment

Automation R5.13 adds a management-only form for an approved order in preparation, ready, or partially dispatched state. It accepts exact per-model quantities, a reason and carrier details, shows the exact serials to be moved, and requires a final physical-exit confirmation. One-third selection rounds each model's remaining quantity down and is editable.

`POST /api/orders/partial-dispatch` independently requires admin authorization. It validates the entire request, checks selected serials against current ready/unshipped physical order rows, verifies each serial's model, real order owner and positive warehouse location, then calls the original `ghadir_warehouse_exit_items` ledger in the existing transaction. No serial substitution is allowed if the reviewed selection became stale. A stable request identity plus normalized fingerprint makes an identical retry a no-op and rejects identity reuse with different data.

The operation deliberately leaves a physical remainder; final delivery of the whole remainder uses ordinary financial authorization. It never marks the order financially settled, changes invoice values, creates a receipt, changes allocated physical/financial purchase rows, sends SMS or releases unselected serials. A management audit and one shipment batch capture reason, reviewer, time, exact serials, carrier and the unchanged payment status. The existing incomplete-shipment approval remains open so warehouse serialization, customer exit totals and later continuation do not treat all prepared serials as shipped. Generic `تحویل شد` cannot silently complete an open partial exit even when all serials have been prepared.

The finite package patches only the current owner's root entrypoint plus three public dependencies; stale repository index.php is not an installation input. The four-file installer requires original 18 protected-carton checks, exact starting/anchor/final hashes, a private code checkpoint, dependencies before entrypoint publication, readback and service health. Failed publication or health rolls back code. No production state writes are part of deployment. Recovery includes all new operations and public dependencies (131 code files); full recovery remains manual-only.

Validation: synthetic real-route authorization, one-third of fully ready orders, exact subset movement, unchanged payment/invoice/receipts/cartons, request retries, wrong ownership, unknown/duplicate/stale serials, invalid quantities, missing carrier details, final-remainder refusal, staging/tamper and rollback checks. With the privately reconstructed owner source, the same fixture also runs the original warehouse functions; private source never enters this public repository. Android checks cover pure quantity limits and the management form's authorization, confirmation and stable retry after an HTTP failure. No live test orders or inventory writes are used.
